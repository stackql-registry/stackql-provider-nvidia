# Project guidance

This file is the canonical, tool-neutral guidance for work in this repository. Claude Code ([CLAUDE.md](CLAUDE.md)) and GitHub Copilot ([.github/copilot-instructions.md](.github/copilot-instructions.md)) entry points refer here; Codex should use this file directly. Keep project rules here rather than duplicating them in tool-specific files.

## Project scope and architecture

- This repository builds and documents the `nvidia` provider for [StackQL](https://github.com/stackql/stackql): SQL query and provisioning operations against the NVIDIA NGC control plane - NVIDIA Cloud Functions (NVCF: functions and versions, deployments and GPU specifications, cluster groups and GPU inventory, request queues, sharing grants, HTTP-polling invocation), the NGC private registry (models, resources, recipes, generic artifacts such as helm charts, endpoints and blueprints, versions and files, collections, shares, encryption keys), the public NGC catalog, and NGC organizations, teams, users, roles and invitations.
- Scope notes, recorded so they are never relitigated: Run:ai and DGX Cloud Lepton have their own control planes and are reserved future siblings. The NIM / API-catalog inference endpoints (`integrate.api.nvidia.com`) are a data-plane LLM surface, out of scope. Artifact binary push/pull is the registry data plane, skipped (`data-plane-file-transfer`). Streaming and gRPC invocation forms are not in the published spec; the HTTP-polling form is mapped (`nvcf_invocation`). Fleet Command, Base Command batch, subscription/billing and notification definitions are out of scope (recorded in `download_manifest.json`). Container images live under the container registry API, whose definition is not published (NOTES.md, Open 5).
- Archetype: DIRECT, a hybrid of three pinned inputs. Paths, parameters and request bodies come from the vendor's published definitions; response schemas for the registry surface fall back to the pinned `ngcsdk` Python wheel's data classes (response side only). The procedure is the `stackql-provider-development` skill in `.claude/skills/stackql-provider-development/` (`SKILL.md` is the map, `references/*.md` the step procedures, `references/uplift-checklist.md` the entry point for a refresh); read the reference file for a step before executing it. The finished reference repositories are [`stackql-provider-supabase`](../../S/stackql-provider-supabase) and [`stackql-provider-clickhouse`](../../C/stackql-provider-clickhouse); sibling-build NOTES.md findings are reused, not re-derived. nvidia-specific findings live in [NOTES.md](NOTES.md) - read it before changing a mapping.
- NVIDIA publishes a Go Terraform provider ([`NVIDIA/terraform-provider-ngc`](https://github.com/NVIDIA/terraform-provider-ngc)) covering NVCF functions and telemetry endpoints (one resource and one data source each). State that once, factually. This provider's counter is mechanical completeness from the published definitions (335 operations, 7 services, 82 resources plus the `vw_gpu_capacity` view) and the query surfaces that matter: GPU and cluster-group inventory, NVCF fleet state by deployment specification, function sharing audits, registry estate reports, org membership. Capability statements and runnable examples, never editorializing.

## Spec sources (three, all pinned)

1. **NVCF** - `https://api.nvcf.nvidia.com/v3/openapi` (openapi 3.1.0, linked from the NVCF API docs). Management operations are served from `api.ngc.nvidia.com`, queue details and invocation from `api.nvcf.nvidia.com`; the host is carried per service (`nvcf_queues`, `nvcf_invocation` on the nvcf host).
2. **NGC core** - two definitions behind the API explorer at `docs.ngc.nvidia.com/api/`, fetched from pinned URLs by `harvest_ngc_spec.mjs`: `ngc_kas.json` (orgs, teams, users; served publicly at `api.ngc.nvidia.com/v3/api-docs`) and `ngc_models.json` (the Private Artifacts (Models) API: registry and catalog artifact metadata; declared on `models.ngc.nvidia.com/v1/...`, served publicly at `api.ngc.nvidia.com/v2/...` - the clean step rewrites the prefix).
3. **ngcsdk** - `harvest_ngc_sdk_schemas.mjs` downloads the `ngcsdk` wheel from PyPI (pinned version + sha256), parses `registry/data/model/*.py` into JSON Schema (`ngc_sdk_schemas.json`, committed), and `clean_specs.mjs` attaches them as 200 responses to any operation that declares none, by an operationId rule table (`SDK_RESPONSE_CLASSES`). The current models definition ships responses on every operation, so the rule injects nothing today; it stays as the recorded fallback, and a SELECT method left on the bare `Response` envelope fails the inventory.

Pins (URL, date, sha256 of the canonical JSON) are in `provider-dev/config/spec_pin.json`; the downloads are committed (NVIDIA versions none of these URLs). `make fetch-spec` re-downloads and fails on drift; `make refresh-spec` accepts it (review the diff with `node .claude/skills/stackql-provider-development/scripts/spec_diff.mjs <pinned> <fetched>` and record the summary in NOTES.md). The weekly CI job also snapshots the NGC deprecation schedule page (`check_deprecation_page.mjs`, `deprecation_schedule.json`).

## Design decisions (settled - see NOTES.md for the evidence)

- **Authentication** - `bearer` from `NGC_API_KEY` (an NGC Personal API Key, `nvapi-...`), the NVIDIA Terraform provider's and the NGC CLI's variable; `provider-dev/config/provider_config.json` becomes `config:` in `provider.yaml`. Two fixed hosts. A personal key is sent as `Authorization: Bearer` directly; the legacy `$oauthtoken` JWT exchange is not involved (NOTES.md 19, 21a).
- **Scoping** - org scope is a path-level server variable. `bin/split.mjs` rebases every org-scoped operation (leading `/v2/org/{org_name}`, `/v3/orgs/{org_name}`, `/v2/artifact-registry/org/{org_name}`) onto the remainder path; `post_process.mjs` attaches a path-item `servers` template carrying `org_name` with `x-stackQL-envVar: NGC_ORG`. A `WHERE org_name` value beats the environment; unset, `org_name` is required. NVCF paths carry no org (the key implies it). A JOIN cannot fan out on the server variable; the docs teach the two-statement / `UNION ALL` pattern. `orgs.orgs.get` keeps `org_name` as a plain path parameter.
- **The flagship mapping** - the GPU estate: `nvcf_deployments.cluster_groups` (cluster groups with their GPU types and instance types) flattened by the `vw_gpu_capacity` view, and the NVCF fleet state joined to deployment specifications.
- **Deprecation schedule as a build input** - NVIDIA's NGC deprecated API reference ends `/teams/{team}` scoping for NVCF, NVCT, FNDS, Skyway, SIS, SI, PYM, Infinity Manager and GDN on 2026-09-30; `SCHEDULED_DEPRECATIONS` in `build_inventory.mjs` skips those families (`deprecated-schedule-2026-09-30`). Private Registry (and Data Services) team scoping is explicitly exempt, so registry/org team-scoped paths are mapped: `*_by_team` methods on the same resources (they add `team_name` to the signature) and `team_members` / `team_member_roles` / `team_invitations` resources in `orgs`.
- **The service is `private_registry`, not `registry`** - `registry` is a reserved word in the StackQL grammar (`REGISTRY PULL`).
- **Casing** - `snake_case_aliases: true` on the provider plus `request.nativeCasing` on every method: `camel` (NVCF, JSON bodies) or `kebab` (NGC core query parameters such as `page-size`), decided per method by the inventory column `native_casing`. The column rename from the wire spelling is the accepted break; `sanitize-docs` renders kebab parameters as snake_case on the resource pages.
- **Pagination** - NGC core collections page with zero-based `page-number` + `page-size` and echo `paginationInfo {index, totalPages}`; `post_process` configures any-sdk's `page_number` algorithm per list method and pushes `LIMIT` to `page-size` (`queryParamPushdown.top`). NVCF collections are unpaginated. The terminating-page behaviour on the live wire is still owed (NOTES.md 21).
- **objectKey** - list envelopes unwrap their array property, entity envelopes their object property; when several qualify the property named after the resource wins (`modelVersion` for `model_versions`). Entities with array fields (GPU catalog rows) get none.
- **Opaque bodies and scalar lists** - the pexec invocation body is a `{body}` wrapper plus request transform; `function_ids` and the invocation status body are re-shaped by response transforms.
- **Update semantics** - GET list/get `SELECT`, POST create `INSERT`, PATCH/PUT `UPDATE` (PUT is not `REPLACE` without field-drop evidence - keycloak rule; the one PUT with a PATCH twin, `artifacts.replace`, is `REPLACE`), DELETE `DELETE`, actions `EXEC`; grants-as-data for authorizations, shares, roles and team membership (add = `INSERT`, remove = `DELETE`).
- **Skip codes** (160 operations): `service-infra`, `internal-admin`, `deprecated-inline`, `superseded-by-v3-twin`, `non-generator-http-verb`, `data-plane-file-transfer`, `non-json-response`, `non-projectable-response`, `legacy-twin`, `duplicate-endpoint-family`, `inbound-webhook-not-client-api`, `deprecated-schedule-2026-09-30`. Counts are in NOTES.md 11 and the README.
- **Rate limit** - NVIDIA publishes no request limit for these APIs; the smoke harness paces every statement at `INTER_REQUEST_DELAY_S` (0.5 s) and a 429 fails the run as a harness bug, not a retry case.
- **Labels** - vendor `deprecated` markers and summaries flow into the docs as written; inline-deprecated operations with a replacement are skipped (`deprecated-inline`).
- **Engine typing** - `UPDATE` marshals every `SET` value as a string; `INSERT` and `EXEC` send typed JSON; `EXEC` cannot carry a boolean. Documented in the docs header, probed by the smoke suite, not worked around in the provider.
- **Views** - `views/nvcf_deployments/views.yaml` ships `vw_gpu_capacity` (one row per cluster group x GPU x instance type), spliced at generate time and documented like a resource.

## Toolchain and validation

- Latest `@stackql/provider-utils`, `@stackql/pgwire-lite` and `@apidevtools/swagger-parser` (check npm before starting: `npm view @stackql/provider-utils version`); Docusaurus `^3.10.x`. Node >= 22.19 (Node 20 reached end of life in April 2026; swagger-parser 13 needs 22.19), `type: module`. `js-yaml` stays on 4.x (provider-utils emits with js-yaml 4; v5 drops the default export and changes scalar quoting, so that bump is coordinated with provider-utils). `package-lock.json` pins what CI installs; a toolchain bump is an explicit commit that regenerates the artifacts.
- Linux, macOS or WSL (WSL is the execution environment on the maintainer's machine: GNU make, bash, the latest `stackql` release on PATH, Python 3, yarn; keep the smoke venv off the DrvFs mount with `make smoke VENV=$HOME/.venvs/stackql-nvidia`). The Makefile is the operator surface (`make help`); the two provider-utils CLI entry points are npm scripts invoked through `node`, never `.bin` shims, flags after `--`.
- `make all` = `deps fetch-spec build test docs website`: pin verify (network, fails on drift) -> pin-check -> clean-specs -> inventory -> split -> mappings -> pre-normalize -> normalize -> generate (+ post-process, views, GraphQL merge) -> test-offline -> test-integration -> test-meta -> docs -> website. It never needs credentials and never bills. `build` deliberately verifies the committed downloads offline (`pin-check`) rather than re-downloading (three documents plus a 2.4 MB wheel). Every step is deterministic and re-runnable; manual decisions are rules in scripts (the classify functions and `SCHEDULED_DEPRECATIONS` in `build_inventory.mjs`, response-class rules and fix classes in `clean_specs.mjs`, passes in `pre_normalize.mjs`, numbered rules in `post_process.mjs`), never hand-edits to CSVs, specs or generated output. `endpoint_inventory.csv` is the single source of truth every later step reads; `all_services.csv` is the committed operation -> resource.method contract and a diff there is a breaking-change review, not noise. Validate-and-fail-without-writing is the standard for every script.
- Tests, in order after every regeneration: `make test-offline` (`SHOW`/`DESCRIBE` against the local file registry: services, resources, verbs, the `NGC_ORG` behaviour, snake aliases, transforms, the view), `make test-integration` (the mock NGC + NVCF API in `tests/integration/mock_nvidia_server.mjs`, both hosts, bearer enforced, row-level and wire-level assertions per archetype; `npm run probe -- "<sql>"` for ad-hoc binding checks), `make test-meta` (the meta-route walk; a resource with no columns fails it - fix the mapping, never the test). Then `make smoke` / `smoke-live` / `smoke-read-only` / `smoke-nvcf` / `smoke-cleanup` from `.env` (`NGC_API_KEY`, `NGC_ORG`, optional `NGC_TEAM`, `NVCF_SMOKE_CONTAINER_IMAGE`): tiered by what the key can reach, everything named `stackql-smoke-<stamp>`, breadcrumbs swept first; only the gated `smoke-nvcf` target deploys anything (smallest instance, always torn down).
- Never run tests against a production organization. The live run still owed with an entitled key is listed in NOTES.md 21; the key last tried is recorded as invalid by NVIDIA's own validator (NOTES.md 21b).

## Documentation and publishing

- `make docs` (generate with `--snake-case-aliases` and `--source-project $(SOURCE_PROJECT)`, then `sanitize-docs`) and `make website`; `website/docs` is committed after every regeneration so pages stamp with their regeneration date. `headerContent1.txt` is the landing-page front matter and pitch; `headerContent2.txt` the getting-started page, closing with `## Example Queries` in the shape every provider site shares.
- Publishing is a separate, human-in-the-loop step: push the generated `provider-dev/openapi/src/nvidia` directory to `providers/src` in a feature branch of [`stackql-provider-registry`](https://github.com/stackql/stackql-provider-registry), follow the registry release flow, verify with `REGISTRY PULL nvidia` from the dev registry and `make smoke-live`. The microsite deploys to GitHub Pages (`nvidia-provider.stackql.io` CNAME -> `stackql.github.io.`); the provider is listed in the Providers menu by adding it to `src/configs/providers.json` in the `stackql.io` repository.

## Writing conventions

These apply to every piece of text the build generates: README, docs headers and examples, NOTES, this file, code comments, commit messages, console output, inventory and CSV columns, mock fixtures. Text the vendor owns (operation summaries, schema and parameter descriptions, the pinned snapshots, `provider-dev/source`, the generated provider and `website/docs`) is passed through as the vendor wrote it; the only alteration is the MDX escaping `sanitize-docs` applies.

- Measured, precise copy, no hyperbole; third-person or passive framing for descriptive copy. The Terraform provider is mentioned once, factually.
- No em dashes and no `--` as a dash; use `-`. No characters that are not on a QWERTY keyboard: no emoji, no typographic quotes, `->` for arrows. No stacked headings.
- Sample queries follow the k8s README style: realistic, runnable against the generated surface, snake_case names, `json_extract` for nested fields, parser keywords double-quoted.

## Non-negotiables

1. Latest `@stackql/provider-utils`, always
2. The skill is the procedure; the supabase / clickhouse repos are the reference pattern; sibling-build NOTES.md findings are reused, not re-derived - deviate only with a documented reason in NOTES.md
3. The three upstream inputs are pinned with evidence; the response-side SDK derivation is a recorded decision in `spec_pin.json` and `download_manifest.json`, never a silent switch
4. The deprecation schedule is a build input: scheduled families are never mapped, exempt families are never blanket-skipped
5. Deterministic scripts, never hand-edits to derived artifacts
6. Every regeneration is followed by `make test` before commit
7. Test harnesses pace under the rate limit - a 429 in CI is a harness bug
8. Smoke tests clean up everything they create and never leave a deployed function running - a failed run must not leave GPU-billing resources behind
